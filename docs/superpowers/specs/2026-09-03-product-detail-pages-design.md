# Дизайн: індексовані сторінки товару (шини/диски)

Дата: 2026-09-03

## Мета

Зараз каталог шин/дисків показує лише картки в межах домашньої сторінки; окремого,
індексованого в Google URL на конкретний товар немає. Потрібно: клік на картку товару
відкриває окрему сторінку з фото, назвою, характеристиками і кнопкою "Купити", і ця
сторінка має власний постійний URL, який Google реально індексує, а Telegram/Facebook
коректно показують у прев'ю посилання.

## Контекст і обмеження

- Сайт — статичний Vite/vanilla TS build без бекенду й без SSR-фреймворка. Дані товарів
  фетчаться в браузері з Google Sheets CSV (`src/js/sheets.ts`, `render-products.ts`) —
  на етапі білда їх за замовчуванням немає.
- Деплой: GitHub Actions (`.github/workflows/deploy.yml`) на push у `main` — `npm run
  build` → FTP-заливка `dist/` на adm.tools (Apache-хостинг).
- Уже є прецедент пост-білд генерації додаткової статичної сторінки:
  `scripts/generate-ru-html.mjs` клонує готовий `dist/index.html`, підмінює
  мета-теги і переписує відносні шляхи на кореневі для `dist/ru/index.html`. Новий
  функціонал слідує тому самому патерну.
- Товари не мають стабільного id/slug у таблиці — рішення (підтверджено користувачем):
  генерувати slug автоматично з існуючих колонок, без зміни структури таблиці.
- Каталог ~100–1000 товарів (шини+диски) — генерація статичної сторінки на кожен товар
  під час білда є практичною за часом і розміром.
- Повна індексація в Google важлива → потрібен справжній унікальний HTML на кожному
  URL до виконання JS (не чистий client-side рендер).
- Прийнятна періодична (не миттєва) свіжість даних товару після редагування таблиці.

## Рішення: пререндер сторінок товару під час білда

### 1. URL і slug

- `/tires/<slug>/index.html` і `/wheels/<slug>/index.html` — кожна директорія віддає
  `index.html` за замовчуванням (Apache), URL виглядає як `/tires/<slug>/`.
- Slug для шини: `${brand}-${model}-${width}-${profile}-r${diameter}-${season}`
  (сезон додано, щоб літня/зимова версія того самого розміру не збігались).
- Slug для диска: `${brand}-${model}-r${diameter}-j${width}-pcd${pcd}-et${et}`.
- Нормалізація: транслітерація кирилиці в латиницю, lowercase, заміна всього, що не
  `[a-z0-9]`, на `-`, згортання повторних `-`, обрізання по краях.
- Дедуплікація: якщо після нормалізації два рядки дають однаковий slug, до другого й
  наступних додається суфікс `-2`, `-3`... за порядком рядків у CSV; у консоль білда
  виводиться попередження з обома вихідними рядками, щоб це було видно в CI-логах.
- **Відома межа:** slug рахується з полів, які може редагувати власник таблиці.
  Перейменування бренду/моделі чи істотна зміна порядку рядків може змінити slug і
  "зламати" раніше розшарені посилання. Прийнято як допустимий ризик.

### 2. Джерело даних для білд-скрипта

- `src/data/sheet-ids.json` — новий файл, тримає `spreadsheetId` і `gid` для шин/дисків
  (і, за бажанням, контенту), які зараз захардкоджені в `src/config.ts`.
- `src/config.ts` імпортує цей JSON (`resolveJsonModule` вже `true` в tsconfig) і
  будує URL через існуючий `sheetCsvUrl()` — єдине місце для URL зберігається.
- Новий `scripts/generate-product-pages.mjs` імпортує той самий JSON напряму (Node ESM
  підтримує імпорт `.json` без транспайлера) і локально повторює тривіальну функцію
  `sheetCsvUrl()`, щоб зібрати ті самі CSV-URL без залежності від TS-модуля.
- Фетч CSV — вбудований `fetch` (Node 20+), парсинг — `papaparse` (вже продакшн-залежність,
  працює і в Node).
- **Відома межа (свідомо прийнята):** трансформація "рядок CSV → назва/характеристики
  товару" (аналог `tiresDescribe`/`wheelsDescribe` з `render-products.ts`) буде
  продубльована у скрипті звичайним JS, а не імпортована — бо `.mjs`-скрипт у CI на
  Node 20 не може напряму імпортувати `.ts`, а додавати транспайлер (`tsx`/`ts-node`)
  лише для цього суперечить мінімалістичному підходу проєкту (без зайвих залежностей,
  без фреймворків). Ризик того самого класу, що вже задокументований у CLAUDE.md для
  відповідності `FieldDef`-ключів і заголовків таблиці: зміна формули заголовка/специфікацій
  товару в одному місці вимагає ручного оновлення й у другому.

### 3. Побудова HTML сторінки товару

- В `index.html` додаються HTML-коментарі-маркери навколо header (з навігацією й
  іконкою кошика), розмітки cart-drawer і footer, напр. `<!-- SITE_HEADER_START -->`
  / `<!-- SITE_HEADER_END -->` і аналогічно для cart-drawer/footer.
- `generate-product-pages.mjs` читає вже зібраний `dist/index.html`, вирізає ці три
  блоки (header, cart-drawer, footer) і блок `<script type="module" src="...">` в
  кінці `<body>` — і складає з них новий каркас, спільний для всіх сторінок товару.
- Для кожного товару в цей каркас вставляється `<main>` з: фото (або плейсхолдер),
  назвою, списком характеристик, ціною, статусом наявності, кнопкою "Купити" і
  посиланням "← Назад до каталогу" (`/#tires` або `/#wheels`).
- Оскільки сторінка лежить на рівень глибше (`dist/tires/<slug>/index.html`), усі
  відносні шляхи (`./assets/...`) переписуються на кореневі (`/assets/...`) — той
  самий прийом, що вже застосований у `generate-ru-html.mjs` для `/ru/`.
- Той самий бандл `main.js`/`main.css`, що й на головній сторінці, підключається без
  змін — окремого Vite-entry для сторінки товару не потрібно. `initCatalogs()` та інші
  `init*()`-функції з `main.ts` мають безпечно ігнорувати відсутні на цій сторінці DOM-вузли
  (каталог, hero-slider, карта) — `initCatalogs`/`render-products.ts` вже так поводиться
  (try/catch навколо `requireEl`); інші модулі (`hero-slider.ts`, `map.ts`, `content.ts`)
  будуть перевірені й, де потрібно, захищені аналогічно на етапі імплементації.

### 4. SEO-теги й структуровані дані

Кожна сторінка товару отримує власні:
- `<title>`, `meta description`, `<link rel="canonical">`.
- `og:title`, `og:description`, `og:url`, `og:image` (фото товару, якщо є, інакше —
  дефолтне фото вивіски магазину, що вже використовується на головній), `twitter:*`.
- JSON-LD `Product`: `name`, `image`, `sku` (= slug), `offers.price`,
  `offers.priceCurrency = "UAH"`, `offers.availability` (InStock/OutOfStock за
  `in_stock`), `offers.url`.

### 5. Кнопка "Купити" і кошик

- Дані товару, потрібні кнопці (`key`, `title`, `sizeLine`, `price`), вбудовуються в
  сторінку як `<script type="application/json" id="product-data">`.
- Невеликий інлайн-скрипт (частина спільного `main.js`, або маленький додатковий
  модуль) читає цей JSON і на клік кнопки викликає той самий `addItem()` з
  `src/js/cart.ts`, що й картка каталогу — кошик і дравер лишаються спільними між
  каталогом і сторінками товару.

### 6. Sitemap

`generate-product-pages.mjs` після генерації сторінок перезбирає `dist/sitemap.xml`:
копіює наявні статичні записи (`/`, `/ru/`) з `public/sitemap.xml` і додає по одному
`<url>` на кожну згенеровану сторінку товару (з `lastmod` = час білда).

### 7. Оновлення `package.json` і білд-пайплайну

```json
"build": "vite build && node scripts/generate-ru-html.mjs && node scripts/generate-product-pages.mjs"
```

Порядок між `generate-ru-html.mjs` і `generate-product-pages.mjs` не критичний — обидва
лише читають `dist/index.html` і додають нові файли, не змінюючи його.

### 8. Свіжість даних — плановий ребілд

До `.github/workflows/deploy.yml` додається `schedule:` тригер (напр. `cron: '0 */6 * *
*'`, кожні 6 годин) поруч із наявними `push`/`workflow_dispatch`. Той самий job
(`npm run build` + FTP-деплой) підхоплює зміни в таблиці (нова ціна, статус наявності,
нові товари) без потреби в пуші коду. Якщо на білді фетч таблиці впаде (мережа/тимчасова
недоступність) — скрипт логує попередження й не генерує сторінки товарів у цьому запуску,
але решта сайту (включно з клієнтським каталогом, що фетчить дані самостійно в браузері)
білдиться і деплоїться штатно.

### 8.1. Ручний запуск оновлення з адмінки

Окрім розкладу, власник має можливість запустити оновлення одразу, не чекаючи
наступного вікна `schedule`:

- У тулбарі `/admin` (`src/admin/main.ts`, поруч із кнопкою "Вийти") — нова кнопка
  "Оновити товари зараз".
- Клік викликає `callApi('rebuildProducts', { password })` — той самий Apps Script Web
  App (`admin/apps-script/Code.gs`), що вже обробляє `save`/`listOrders`/`order`.
- У `Code.gs`: нова дія в `doPost` — перевірка пароля через існуючий `checkPassword_`,
  далі `UrlFetchApp.fetch` на GitHub REST API
  (`POST /repos/<owner>/<repo>/actions/workflows/deploy.yml/dispatches`, body
  `{"ref":"main"}`), що запускає вже наявний у `deploy.yml` тригер `workflow_dispatch`
  — тобто той самий job (`npm run build` + FTP-деплой), не чекаючи `schedule`.
- Токен для GitHub API — новий Script Property `GITHUB_TOKEN` (fine-grained PAT,
  права лише "Actions: write" на цей репозиторій), за тим самим принципом, що вже
  застосований для `BOT_TOKEN`/`CHAT_ID` — секрет живе тільки на сервері Apps Script,
  у браузер не потрапляє.
- Відповідь адмінці — просто підтвердження запуску ("Оновлення запущено, зміни
  з'являться на сайті протягом кількох хвилин"), без опитування статусу білда: це
  зайва складність, не потрібна для цієї задачі (прогрес видно й так — на самому сайті
  або в GitHub Actions).
- Дублікати запуску не шкодять: `deploy.yml` вже має
  `concurrency: { group: deploy, cancel-in-progress: true }` — повторний клік просто
  скасовує попередній запуск і стартує новий.

### 9. Інтеграція з каталогом

`renderCard()` у `render-products.ts` обгортає картку/заголовок у `<a
href="/tires/<slug>/">` (або `/wheels/<slug>/`), використовуючи ту саму формулу slug,
продубльовану на клієнті чистою функцією (без DOM/i18n залежностей) — той самий клас
ризику, що описаний у пункті 2 (потрібно синхронно підтримувати формулу в трьох місцях:
клієнт, build-скрипт, і візуально — заголовки колонок таблиці).

## Файли, які створюються/змінюються

- **Нові:** `src/data/sheet-ids.json`, `scripts/generate-product-pages.mjs`,
  можливо `src/styles/product-detail.css` (підключається в `src/styles/main.css`).
- **Змінюються:** `src/config.ts` (читає `sheet-ids.json`), `index.html` (маркери
  header/cart-drawer/footer), `render-products.ts` (посилання на картці, спільна
  slug-функція), `package.json` (крок білда), `.github/workflows/deploy.yml`
  (`schedule` тригер, `workflow_dispatch` вже наявний), `public/sitemap.xml`-логіка
  (генерується поверх у `dist/`), `admin/apps-script/Code.gs` (нова дія
  `rebuildProducts` + Script Property `GITHUB_TOKEN`), `src/admin/main.ts`/`api.ts`
  (кнопка "Оновити товари зараз" у тулбарі).

## Тестування/перевірка

- `npm run build && npm run preview` — вручну перевірити 2–3 згенеровані сторінки
  товару (шина й диск), коректність шляхів до ассетів, роботу кнопки "Купити"
  (додавання в кошик), посилання "назад до каталогу".
- Перевірити `dist/sitemap.xml` містить очікувану кількість `<url>`.
- `npm run typecheck` — без помилок після змін у `config.ts`.
- Ручна перевірка одного товару через Google Rich Results Test / Google Search
  Console URL Inspection (поза CI, вручну власником сайту) — підтвердити, що JSON-LD і
  мета-теги валідні.
- Відомий пробіл: `npm run dev` не показує сторінки товару (немає dev-прев'ю), як і
  зараз немає dev-прев'ю для `/ru/` — це наявне обмеження проєкту, не регрес.
- Кнопку "Оновити товари зараз" перевірити вручну: клік у `/admin` реально запускає
  новий run у GitHub Actions (вкладка Actions репозиторію), і після його завершення
  сторінки товарів у `dist`/на сайті оновлені.

## Явно поза межами цього дизайну

- Реальний backend/CMS для товарів — дані й надалі живуть у Google Sheets.
- Гарантована миттєва свіжість цін/наявності на сторінці товару — прийнята періодична
  свіжість через ребілд за розкладом.
- Пагінація/категорійні лендинги (напр. "зимові шини Кривий Ріг") — окрема задача,
  не входить у цей дизайн.
